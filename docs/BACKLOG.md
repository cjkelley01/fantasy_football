# Development backlog

This is the authoritative list of **outstanding development work** in `tdkelley2001/fantasy_football`. [README](../README.md#current-capabilities) describes current capabilities; the [domain references](../README.md#understand-the-system) own technical requirements under [authority precedence](../AGENTS.md#authority-and-precedence). A proposal or priority does not authorize implementation, waive a requirement or approve release.

## Maintaining this file

- **Add:** propose a bounded item through an ordinary PR. Reuse an existing item where scopes overlap. Give it a stable descriptive anchor, scope, type/priority, status, dependencies or acceptance gate and optional owner; preserve existing WR references.
- **Claim:** coordinate overlapping changes, agree ownership and set In Progress only when scope is authorized and dependencies permit work. Unassigned work is valid.
- **Update:** keep status, blockers and evidence truthful in the work PR or a small coordination PR. Use In Review while necessary acceptance or merge is pending. A small coordination PR can publish in-flight status and the implementation PR link on main. Routine coordination follows the ordinary PR approval policy.
- **Complete:** after acceptance and merge, update the owning documentation to describe the current system and remove the item. Git and the merged PR retain the decision and verification record; there is no completed-work register. Remove a declined/duplicate proposal only after its disposition is agreed.

Types: Bug, Enhancement, Documentation, Technical debt, Research. Priorities: **P0 critical**, **P1 high**, **P2 normal**, **P3 low**; no P0 is asserted here. Statuses: Backlog, Ready, In Progress, In Review, Blocked. Ready requires scope approval and satisfied dependencies; Blocked records the reason and unblocking step. Owner `—` means unassigned. Follow [CONTRIBUTING](../CONTRIBUTING.md) for branch/fork workflow and verification.
